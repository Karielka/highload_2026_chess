# Проектирование высоконагруженного сервиса совместной работы с документами

Курсовая работа по дисциплине «Проектирование высоконагруженных систем».

## 1. Тема и целевая аудитория

### Тип сервиса

Сервис для создания, хранения и совместного редактирования документов (аналог Notion).

### Целевая аудитория

В качестве основного рыночного ориентира для проектируемого сервиса рассматривается **Notion**. Сервис используется как частными пользователями, в том числе студентами и молодыми специалистами, так и рабочими командами и компаниями. Проектируемая система ориентирована преимущественно на пользователей в возрасте **18–34 лет** [[5]](#source5), а также на рабочие команды численностью до 200 участников.

В августе 2024 года Notion преодолел отметку в **100 млн пользователей** [[1]](#source1). При этом компания публично не раскрывает значения MAU и DAU для всей платформы, поэтому при проектировании нагрузки используются собственные расчётные показатели.

Внешние оценки подтверждают значительную активную аудиторию сервиса. По данным AICPB, мобильное приложение Notion в июне 2026 года имело около **8,2 млн MAU** [[4]](#source4). Кроме мобильных приложений, значительная часть пользователей работает с Notion через веб- и desktop-клиенты, поэтому суммарная активная аудитория сервиса существенно выше мобильного MAU.

Для дальнейшего проектирования высоконагруженной системы принимаются следующие целевые показатели:

| Метрика                         | Значение |
| ------------------------------- | -------: |
| Зарегистрированные пользователи | 100+ млн |
| Месячная аудитория (MAU)        |   20 млн |
| Дневная аудитория (DAU)         |    5 млн |
| DAU / MAU                       |      25% |

Значения **MAU = 20 млн** и **DAU = 5 млн** являются проектным допущением и используются для последующего расчёта RPS, объёма хранилища, сетевого трафика и требований к масштабированию. Они не являются официальными метриками Notion.


#### География аудитории

Notion изначально имеет международную аудиторию. Ещё в 2021 году компания сообщала, что **более 80% пользователей находились за пределами США**, а сервис использовался пользователями как минимум из 28 стран [[6]](#source6). В настоящее время Notion указывает присутствие более чем в 50 странах [[2]](#source2).

По оценке Similarweb для `notion.com` за август 2026 года, крупнейшие источники веб-трафика распределялись следующим образом [[5]](#source5):

| Страна        | Доля веб-трафика |
| ------------- | ---------------: |
| США           |           17,27% |
| Южная Корея   |           11,87% |
| Япония        |            9,73% |
| Бразилия      |            4,28% |
| Индия         |            4,22% |
| Другие страны |           52,63% |

Таким образом, проектируемый сервис должен рассматриваться как **глобальная система**, аудитория которой распределена между Северной Америкой, Европой, Азией и другими регионами. Это необходимо учитывать при дальнейшем проектировании географического размещения инфраструктуры, CDN, файлового хранилища и механизмов репликации данных.


### Функционал MVP

1. **Регистрация и авторизация.** Регистрация по электронной почте, вход по паролю или OAuth, завершение активных сессий и восстановление доступа.
2. **Рабочие пространства.** Создание рабочего пространства, приглашение и удаление участников, роли `owner`, `editor` и `viewer`.
3. **Работа с документами.** Создание и удаление документов, вложенная иерархия страниц, добавление, изменение, удаление и перемещение блоков.
4. **Совместное редактирование.** Одновременная работа нескольких пользователей на одной странице, отображение присутствующих участников, отображение изменений в реальном времени.
5. **Поиск.** Полнотекстовый поиск по названию и содержимому доступных пользователю документов внутри выбранного рабочего пространства.
6. **Файлы и изображения.** Загрузка, скачивание и отображение вложений внутри документа; права на файл наследуются от страницы.

### Ключевые продуктовые решения

1. Документ состоит из упорядоченных блоков. Каждый блок можно изменять и перемещать независимо от остальных.
2. Рабочее пространство является основной единицей изоляции данных и прав доступа.
3. Изменения документа должны быть видны другим редакторам почти в реальном времени.
4. Для поиска допускается небольшая задержка обновления индекса.
5. Пользовательские файлы не сохраняются непосредственно в основной реляционной базе данных.

## 2. Расчёт нагрузки

В первой части для проектируемого сервиса были приняты **20 млн MAU** и **5 млн DAU**. Эти значения и будем использовать дальше.

Для расчётов нужны данные о том, сколько действий делает пользователь и сколько данных он хранит. Notion такие показатели подробно не публикует, поэтому для численных оценок используется Confluence — близкий по назначению сервис совместной работы с документами. Atlassian публикует как нагрузочный профиль Confluence, так и данные рабочего экземпляра сервиса [[7]](#source7) [[8]](#source8).

Для общего объёма хранения будем считать систему на **100 млн пользовательских аккаунтов**. Это фиксированная расчётная база, соответствующая масштабу, принятому в первой части.

### 2.1. Продуктовые метрики

#### Аудитория

| Метрика | Значение |
| --- | ---: |
| Месячная аудитория (MAU) | 20 млн |
| Дневная аудитория (DAU) | 5 млн |
| DAU / MAU | 25% |
| Пользовательская база для расчёта хранения | 100 млн |

#### Количество действий пользователя

Atlassian использует для нагрузочного тестирования Confluence профиль, построенный по реальному трафику своего внутреннего сервиса. В нём **360 активных пользователей выполняют 19 171 действие в час** [[7]](#source7).

Из всего набора действий нам нужны только те, которые соответствуют MVP нашего сервиса:

| Действие | Количество в час на 360 пользователей |
| --- | ---: |
| Открытие страницы | 4 823 |
| Поиск | 716 |
| Редактирование страницы | 660 |
| Создание страницы | 230 |
| Загрузка вложения | 861 |

Чтобы перейти от часовой нагрузки к дневной, принимается **6 часов активной работы в сутки**. Такое окно не взято случайно: Atlassian публикует отдельный шестичасовой срез обычного рабочего дня с 09:00 до 15:00, в который попадают и пики, и спады нагрузки [[8]](#source8).

Например, для открытия документа:

```text
4 823 / 360 × 6 = 80,4 открытия в день
```

Аналогично считаются остальные действия.

Для просмотра вложений в старом нагрузочном профиле отдельной строки нет. Поэтому используется отношение из более свежего отчёта Confluence 10.2: в одном тестовом прогоне было **1 184 просмотра вложений** и **1 353 загрузки** [[10]](#source10).

Итоговый профиль пользователя:

| Действие | В среднем на пользователя в день | Всего при 5 млн DAU |
| --- | ---: | ---: |
| Открытие документа | 80,4 | 401,9 млн |
| Поиск | 11,9 | 59,7 млн |
| Редактирование документа | 11,0 | 55,0 млн |
| Создание документа | 3,8 | 19,2 млн |
| Загрузка вложения | 14,4 | 71,8 млн |
| Просмотр / скачивание вложения | 12,6 | 62,8 млн |
| **Итого** | **134,1** | **670,3 млн действий/сутки** |

Регистрация, восстановление доступа и управление участниками рабочего пространства в эту таблицу не включены. Это сравнительно редкие операции, и для них нет опубликованной частоты, на основании которой можно было бы сделать такой же расчёт.

#### Средний объём данных пользователя

Для оценки количества документов и вложений используется рабочий экземпляр Confluence компании Atlassian. На момент опубликованного среза в нём было **686 тыс. страниц**, **2,424 млн вложений** и **11 тыс. пользовательских аккаунтов** [[8]](#source8).

Отсюда:

```text
686 000 / 11 000 = 62,4 документа на пользователя

2 424 000 / 11 000 = 220,4 вложения на пользователя
```

Размеры самих объектов берутся из другого официального среза Confluence [[9]](#source9):

- 517 520 записей с содержимым занимали 1 354 МБ;
- 207 659 файлов-вложений занимали 105 ГБ;
- поисковый индекс занимал 3,9 ГБ на 623 155 записей контента.

Средний размер получается следующим:

```text
Документ:       1 354 МБ / 517 520 = 2,62 КБ
Вложение:       105 ГБ / 207 659 = 0,506 МБ
Поисковый индекс: 3,9 ГБ / 623 155 = 6,26 КБ на объект
```

Получаем:

| Тип данных | В среднем на пользователя | Объём на пользователя |
| --- | ---: | ---: |
| Документы | 62,4 шт. | 0,16 МБ |
| Вложения | 220,4 шт. | 111,42 МБ |
| Поисковый индекс | 62,4 объекта | 0,39 МБ |
| **Итого** | — | **около 112 МБ** |

Основной объём пользовательских данных приходится на вложения. Поэтому хранить файлы непосредственно в основной БД нецелесообразно: в БД достаточно хранить их метаданные и ссылку на объектное хранилище.

### 2.2. RPS

Для среднего RPS используется обычная формула:

```text
RPS = количество операций в сутки / 86 400
```

Пиковая нагрузка считается по данным рабочего экземпляра Atlassian. В опубликованном шестичасовом срезе средняя нагрузка составляла **341 тыс. HTTP-запросов в час**, а максимальная — **456 тыс.** [[8]](#source8).

Коэффициент пиковой нагрузки:

```text
456 000 / 341 000 = 1,34
```

То есть:

```text
RPSpeak = RPSavg × 1,34
```

Для расчёта считается, что одному основному действию пользователя соответствует один логический запрос нашего API.

| Запрос | Операций в сутки | Средний RPS | Пиковый RPS |
| --- | ---: | ---: | ---: |
| `GET /documents/{id}` | 401,9 млн | 4 652 | 6 221 |
| `GET /search` | 59,7 млн | 691 | 923 |
| `POST /transactions` | 55,0 млн | 637 | 851 |
| `POST /documents` | 19,2 млн | 222 | 297 |
| `POST /files` | 71,8 млн | 830 | 1 111 |
| `GET /files/{id}` | 62,8 млн | 727 | 972 |
| **Итого** | **670,3 млн** | **7 758 RPS** | **10 374 RPS** |

Здесь считаются именно основные запросы API. Дополнительные запросы браузера за статическими ресурсами в таблицу не входят.

Совместное редактирование использует постоянные WebSocket-соединения. Notion также применяет WebSocket для передачи изменений между клиентами [[11]](#source11). Отдельный численный коэффициент для рассылки изменений здесь не вводится, поскольку нет открытых данных о среднем количестве одновременно работающих редакторов одного документа.

### 2.3. Размер хранения

Теперь пересчитаем средние значения на **100 млн пользовательских аккаунтов**.

Количество документов:

```text
100 000 000 × 62,4 ≈ 6,24 млрд документов
```

Количество вложений:

```text
100 000 000 × 220,4 ≈ 22,04 млрд вложений
```

Сводная таблица хранения:

| Тип данных | Количество | Средний размер | Общий объём |
| --- | ---: | ---: | ---: |
| Документы | 6,24 млрд | 2,62 КБ | 16,3 ТБ |
| Вложения | 22,04 млрд | 0,506 МБ | 11 142,4 ТБ |
| Поисковый индекс | 6,24 млрд объектов | 6,26 КБ | 39,0 ТБ |
| **Итого** | — | — | **около 11 198 ТБ ≈ 11,2 ПБ** |

Это объём пользовательских данных без учёта репликации, резервных копий, истории версий и служебных данных БД.

По расчёту видно, что почти всё место занимают вложения. Следовательно, основной объём хранения должен приходиться на объектное хранилище, а не на реляционную БД.

### 2.4. Сетевой трафик

Для трафика используются те же средние размеры данных из официального примера Atlassian [[9]](#source9).

Средний документ занимает около **2,62 КБ**. Метаданные одной записи контента в том же срезе занимают около **0,74 КБ**, поэтому открытие документа оценивается в:

```text
2,62 + 0,74 = 3,36 КБ
```

Для поиска в проектируемом API принимается выдача до **20 результатов**:

```text
20 × 0,74 = 14,8 КБ
```

Среднее вложение занимает **0,506 МБ**.

Суточный трафик считается по формуле:

```text
Трафик за сутки = количество операций × средний размер сообщения
```

Для пиковой пропускной способности используется тот же коэффициент `1,34`:

```text
Пиковая скорость =
трафик за сутки × 8 / 86 400 × 1,34
```

| Тип трафика | Средний размер | Трафик за сутки | Пик |
| --- | ---: | ---: | ---: |
| Открытие документов | 3,36 КБ | 1 348 ГБ | 0,17 Гбит/с |
| Поиск | 14,8 КБ | 879 ГБ | 0,11 Гбит/с |
| Редактирование | 2,62 КБ | 144 ГБ | 0,02 Гбит/с |
| Создание документа | 3,36 КБ | 64 ГБ | 0,01 Гбит/с |
| Загрузка вложений | 0,506 МБ | 36 302 ГБ | 4,49 Гбит/с |
| Скачивание вложений | 0,506 МБ | 31 748 ГБ | 3,93 Гбит/с |
| **Итого** | — | **70 484 ГБ/сутки ≈ 70,5 ТБ/сутки** | **8,73 Гбит/с** |

Если разделить нагрузку по назначению, получаем:

| Контур | Трафик за сутки | Пиковая скорость |
| --- | ---: | ---: |
| API сервиса | 2 435 ГБ | 0,30 Гбит/с |
| Файлы / CDN | 68 049 ГБ | 8,43 Гбит/с |
| **Итого** | **70 484 ГБ** | **8,73 Гбит/с** |

Таким образом, основной сетевой трафик создают не текстовые документы, а пользовательские файлы. Их загрузку и скачивание лучше обслуживать через объектное хранилище и CDN, не пропуская бинарные данные через серверы API.

Трафик совместного редактирования по WebSocket в итоговую цифру не включён. Его можно корректно посчитать только после фиксации формата сообщения и среднего числа одновременно работающих пользователей в документе.
