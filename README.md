# Проектирование высоконагруженной платформы онлайн-шахмат

## 1. Тема и целевая аудитория

### 1.1. Тема

Проектируется сервис для игры в шахматы онлайн.

Основной аналог - **Chess.com**. Также к сервисам этого типа относится Lichess.

В работе рассматривается только основной игровой функционал. Обучение, боты, трансляции, клубы и другие дополнительные возможности Chess.com в проект не входят.

### 1.2. Целевая аудитория

Chess.com - глобальный сервис.

По отчёту Chess.com за II квартал 2026 года средняя дневная аудитория составляет **10,2 млн DAU**. На 30 июня 2026 года в сервисе было зарегистрировано более **267 млн пользователей** [[1]](#source1).

По данным официальной страницы Chess.com, месячная аудитория сервиса составляет более **50 млн пользователей в месяц** [[2]](#source2).

Аудитория распределена по всему миру. По данным Chess.com за июнь 2026 года, только на США и Индию приходится **84 млн зарегистрированных пользователей**, то есть примерно треть всей пользовательской базы. В России зарегистрировано 8,1 млн пользователей [[3]](#source3).

Для проектирования принимается глобальная аудитория Chess.com.

| Метрика | Значение |
| --- | ---: |
| MAU | 50+ млн |
| Средний DAU | 10,2 млн |
| Зарегистрированные пользователи | 267+ млн |
| География | Международная |

### 1.3. Функционал MVP

В MVP входят основные функции, необходимые для онлайн-игры:

1. Поиск соперника (матчмейкинг с учетом рейтинга пользователя).
2. Проведение партии - сервер принимает ходы, проверяет их и передаёт состояние партии сопернику.
3. Завершение партии (с пересчетом рейтинга и анализом партии).
4. Анализ партии - подсчет точности, подбор лучших ходов в каждой позиции (проводит серверная модель Stockfish).
5. Жалоба на нечестную игру.
6. Просмотр истории партий (с поиском по сопернику, виду партии, контролю времени).

### 1.4. Ключевые продуктовые решения

- Ходы передаются между игроками в реальном времени.
- Шахматные часы считаются на сервере, а не на клиенте.
- Одна завершённая партия хранится один раз и связывается с обоими игроками.
- Анализ сыгранной партии производится 1 раз и хранится.
- Матчмейкинг учитывает рейтинг игрока и выбранный контроль времени.

## 2. Расчёт нагрузки

Основные данные Chess.com за 2 квартал 2026 года [[1]](#source1):

- **10,2 млн DAU**;
- **2,8 млрд игр за квартал**;
- **380+ игр/с в пике**;
- **540+ млрд обработанных запросов за квартал**;
- **3,3 млн Fair Play reports за квартал**.

Chess.com не публикует долю игр отдельно от игр с ботами. Поэтому 2,8 млрд используется как верхняя оценка нагрузки.

### 2.1. Продуктовые метрики

#### Аудитория

| Метрика | Значение |
| --- | ---: |
| MAU | 50+ млн [[2]](#source2) |
| Средний DAU | 10,2 млн [[1]](#source1) |
| Зарегистрированные пользователи | 267+ млн [[1]](#source1) |

#### Игры и действия пользователя

Среднее количество партий в сутки (во 2 квартале 2026 года 91 день):

```text
2,8 млрд / 91 = 30,77 млн партий/сутки
```

В одной партии участвуют два игрока:

```text
30,77 млн × 2 / 10,2 млн DAU = 6,03 партии на активного пользователя в день
```

Для расчёта количества ходов принимается стандартная для Chess.com расчётная длина партии — **40 полных ходов**, то есть около **80 полуходов** [[5]](#source5).

```text
30,77 млн × 80 = 2,462 млрд ходов/сутки
```

На одного DAU:

```text
2,462 млрд / 10,2 млн = 241,3 хода/сутки
```

Fair Play:

```text
3,3 млн / 91 = 36,3 тыс. жалоб/сутки
```

```text
36,3 тыс. / 10,2 млн = 0,00356 жалобы на DAU в день
```

Анализ партии - продуктовое решение проекта: **каждая завершённая партия анализируется один раз**, результат сохраняется. Game Review на Chess.com также выполняется на сервере с использованием Stockfish [[6]](#source6).

| Действие | На одного DAU в день | Всего в сутки |
| --- | ---: | ---: |
| Участие в партии | 6,03 | 61,54 млн |
| Отправка хода | 241,3 | 2,462 млрд |
| Завершение партии | 3,02 | 30,77 млн |
| Анализ партии | — | 30,77 млн |
| Fair Play report | 0,00356 | 36,3 тыс. |

#### Просмотр истории и анализа

Chess.com не публикует частоту таких запросов.

Для проектируемого API принимается:

- после завершения партии каждый игрок один раз обновляет историю;
- после готовности анализа каждый игрок один раз получает его результат.

Получаем по две операции чтения на одну завершённую партию:

```text
30,77 млн × 2 = 61,54 млн запросов/сутки
```

для истории и столько же для получения анализа.

### 2.2. Средний объём хранения пользователя

Chess.com сообщает о базе из **30+ млрд партий** [[4]](#source4).

Размер внутренней записи Chess.com не опубликован. Для оценки используется открытый PGN-дамп Lichess. За июнь 2026 года в нём:

- **86 483 328 партий**;
- архив занимает **28,2 ГБ**;
- распакованный PGN примерно в **7,1 раза больше** [[7]](#source7).

Средний логический размер одной партии:

```text
28,2 ГБ × 7,1 / 86 483 328 ≈ 2,315 КБ
```

Объём 30 млрд партий:

```text
30 млрд × 2,315 КБ ≈ 69,45 ТБ
```

Среднее число партий в истории одного зарегистрированного пользователя:

```text
30 млрд × 2 / 267 млн ≈ 224,7 партии
```

Так как одна партия хранится один раз и связывается с двумя игроками, нормированный объём архива на аккаунт:

```text
69,45 ТБ / 267 млн ≈ 0,000260 ГБ ≈ 0,260 МБ
```

#### Результаты анализа

Размер результата анализа Chess.com не публикуется, поэтому используется формат проектируемого сервиса.

Для каждой позиции сохраняются:

- оценка позиции;
- класс сыгранного хода;
- лучший ход;
- линия Stockfish примерно на 12 полуходов.

При анализе примерно 80 позиций полезная нагрузка результата анализа принимается равной **≈2,5 КБ** на партию. Это проектный формат хранения, а не значение Chess.com.

```text
30 млрд × 2,5 КБ ≈ 75 ТБ
```

Итого для основных данных MVP:

| Тип данных | Количество | Логический объём |
| --- | ---: | ---: |
| Партии | 30+ млрд | ≈69,45 ТБ |
| Анализы партий | 30+ млрд | ≈75 ТБ |
| **Итого** | — | **≈144,45 ТБ** |

В среднем на зарегистрированный аккаунт:

```text
144,45 ТБ / 267 млн ≈ 0,000541 ГБ ≈ 0,541 МБ
```

Это **логический объём данных**. Репликация, индексы, резервные копии и служебные данные здесь не учитываются.

Прирост в сутки:

```text
Партии:
30,77 млн × 2,315 КБ ≈ 71,2 ГБ/сутки

Анализы:
30,77 млн × 2,5 КБ ≈ 76,9 ГБ/сутки

Итого ≈ 148,1 ГБ/сутки
```

### 2.3. API и RPS

Для среднего RPS:

```text
RPS = число операций в сутки / 86 400
```

Средняя скорость создания партий:

```text
30,77 млн / 86 400 = 356,1 партии/с
```

Chess.com публикует пик **380+ игр/с** [[1]](#source1).

Коэффициент пиковой нагрузки:

```text
Kpeak = 380 / 356,1 ≈ 1,067
```

#### Клиентское API и WebSocket

| Операция | Направление | Что делает | Операций в сутки | Средняя частота | Пик |
| --- | --- | --- | ---: | ---: | ---: |
| `POST /matchmaking/search` | клиент → сервер | Ставит игрока в очередь | 61,54 млн | 712 RPS | 760+ RPS |
| `WS game.move` | клиент → сервер | Передаёт ход | 2,462 млрд | 28 490 EPS | 30 400+ EPS |
| `WS game.end` | сервер → клиент | Передаёт результат и причину завершения: мат, сдача, время, ничья | 61,54 млн | 712 EPS | 760+ EPS |
| `WS game.resign` | клиент → сервер | Игрок сдаётся | ≤30,77 млн | ≤356 EPS | ≤380 EPS |
| `GET /games/history` | клиент → сервер | Возвращает историю с фильтрами | 61,54 млн* | 712 RPS | 760+ RPS |
| `GET /games/{id}/analysis` | клиент → сервер | Возвращает сохранённый анализ | 61,54 млн* | 712 RPS | 760+ RPS |
| `POST /fair-play/reports` | клиент → сервер | Создаёт жалобу | 36,3 тыс. | 0,42 RPS | — |

\* Для истории и анализа принято по одному запросу от каждого игрока после завершения партии.

`game.resign` имеет только верхнюю границу: в одной партии сдаться может не более одного игрока. Доля партий, завершённых сдачей, Chess.com не публикуется.

Мат определяется сервером после `game.move`. Отдельного клиентского запроса для мата нет. После любого завершения сервер отправляет обоим игрокам `game.end`.

Входящий поток без `game.resign`:

```text
712 + 28 490 + 712 + 712 + 0,42 ≈ 30 627 RPS
```

С учётом верхней границы `game.resign`:

```text
≤ 30 983 RPS
```

#### Внутренние операции

После завершения каждой партии сервер выполняет:

| Операция | Средняя частота | Пик |
| --- | ---: | ---: |
| `game.finished` | 356/с | 380+/с |
| Пересчёт рейтинга | 356/с, по 2 игрока | 380+/с |
| Постановка анализа в очередь | 356/с | 380+/с |

Региональный журнал должен выдерживать тот же поток, что и игровой сервис: около **28 490 полуходов/с** в среднем и **30 400+/с** в пике. Это внутренняя запись, а не дополнительный запрос клиента.

При 80 полуходах на партию Stockfish должен обработать:

```text
356,1 × 80 ≈ 28 490 позиций/с
```

В пике:

```text
380 × 80 = 30 400+ позиций/с
```

#### Проверка порядка величины

Chess.com сообщает о **540+ млрд обработанных запросов за Q2** [[1]](#source1):

```text
540 млрд / (91 × 86 400) ≈ 68 681+ запросов/с
```

Наш MVP даёт до **31 тыс. входящих запросов и WS-событий в секунду**. Остальной функционал Chess.com в расчёт не входит.

### 2.4. Сетевой трафик

Размеры сообщений задаются форматом проектируемого API.

| Операция | Размер |
| --- | ---: |
| Matchmaking request/response | ≈192 Б |
| Один ход | ≈208 Б |
| Завершение партии | ≈97 Б на игрока |
| Страница истории, 20 партий | ≈676 Б |
| Результат анализа партии | ≈2,66 КБ |
| Fair Play report | ≈353 Б |

**Matchmaking** содержит идентификатор пользователя, рейтинг и контроль времени. В ответ сервер возвращает `game_id`, данные соперника и цвет фигур.

**Ход** содержит `game_id`, номер хода, начальную и конечную клетки, превращение пешки и время игрока. Учитываются две передачи: игрок → сервер и сервер → соперник.

**Завершение партии** содержит `game_id`, результат, причину завершения и изменение рейтинга. Сообщение отправляется обоим игрокам.

**История партий** возвращает до 20 записей: идентификатор партии, соперника, дату, результат, рейтинг и контроль времени.

**Анализ партии** содержит данные примерно для 80 позиций. Для каждой позиции сохраняются оценка, класс хода, лучший ход и линия Stockfish примерно на 12 полуходов. Полезная нагрузка анализа составляет около **2,5 КБ**. С учётом сетевых заголовков — около **2,66 КБ**.

**Fair Play report** содержит `game_id`, пользователя, причину жалобы и текстовый комментарий.

В размер сетевого сообщения включаются заголовки Ethernet, IPv4, TCP, TLS и WebSocket. Для HTTP-запросов размер заголовков зависит от реализации, поэтому расчёт остаётся приблизительным.

#### Суточный и пиковый трафик

| Тип трафика | За сутки | Пиковая полоса |
| --- | ---: | ---: |
| Matchmaking | ≈11,8 ГБ | ≈0,0012 Гбит/с |
| Ходы | ≈512 ГБ | ≈0,0506 Гбит/с |
| Завершение партии | ≈6,0 ГБ | ≈0,0006 Гбит/с |
| История партий | ≈41,6 ГБ | ≈0,0041 Гбит/с |
| Анализ партии | ≈163,7 ГБ | ≈0,0162 Гбит/с |
| Fair Play | ≈0,01 ГБ | <0,0001 Гбит/с |
| **Итого** | **≈735,1 ГБ/сутки** | **≈0,0727 Гбит/с** |

Основной внешний трафик создают ходы и передача результатов анализа. В таблицу не включены межзонная репликация БД/Kafka и передача резервных копий в облако — они учитываются отдельно при расчёте оборудования.

Для регионального журнала при 128–256 Б на событие и трёх копиях ориентировочный суточный объём записи составляет `2,462 млрд × 128–256 Б × 3 ≈ 0,95–1,89 ТБ` для всей платформы без контрольных точек и накладных расходов Kafka.

## 3. Глобальная балансировка нагрузки

### 3.1. Функциональное разбиение по доменам

| Домен | Назначение |
| --- | --- |
| `api.chess.example` | матчмейкинг, история партий, анализ, Fair Play |
| `game-{region}.chess.example` | игровые WebSocket-соединения |

Матчмейкинг специально вынесен из игрового сервиса для создания легковесных игровых обработчиков.

### 3.2. Расположение ДЦ

Для международной аудитории выбраны пять игровых регионов [[3]](#source3):

| Регион | География |
| --- | --- |
| Virginia | Северная Америка |
| Frankfurt | Европа |
| Mumbai | Индия |
| Singapore | Юго-Восточная Азия |
| São Paulo | Южная Америка |

**Каждый регион содержит три зоны доступности (AZ-A, AZ-B, AZ-C)** с независимыми питанием и сетевой инфраструктурой. Между AZ поддерживается низкая задержка, позволяющая размещать реплики хранилищ в разных зонах. Точное расстояние между площадками определяется AWS; всего в проекте 15 AZ.

Во всех пяти регионах, включая Virginia, работают игровые сервисы, Redis и региональная Kafka. Дополнительно в Virginia размещены основной API, PostgreSQL, архив и центральная Kafka. Сервисы и реплики распределены между AZ. Kubernetes использует `topologySpreadConstraints` и `podAntiAffinity` [[21]](#source21). При потере одной AZ оставшиеся две должны сохранить кворум и обслуживание в пределах региона.

### 3.3. Глобальная балансировка

```text
api.chess.example → Virginia → API
```

Все запросы авторизации, поиска соперника, истории и жалоб идут в Virginia. Matchmaking выбирает один из пяти регионов по задержке обоих игроков и загрузке. После подбора клиенты подключаются к `game-{region}.chess.example` напрямую, не передавая ходы через Virginia.

В каждом регионе внешний **AWS Network Load Balancer (NLB, L4)** распределяет новые TCP-соединения между тремя NGINX в разных AZ. В Virginia тот же внешний NLB обслуживает и API, и игровые WSS по соответствующим доменам. Подробности — в разделе 4.

Полный отказ Virginia ограничивает новые матчи и основной API, но уже начатые партии в остальных регионах могут продолжаться.

### 3.4. Распределение нагрузки

Из раздела 2:

| Операция | Средняя нагрузка | Пиковая нагрузка |
| --- | ---: | ---: |
| Matchmaking | 712 RPS | 760+ RPS |
| Ходы | 28 490 EPS | 30 400+ EPS |
| Завершение партии | 712 EPS | 760+ EPS |
| Сигнал досрочной сдачи | ≤356 EPS | ≤380 EPS |
| История партий | 712 RPS | 760+ RPS |
| Получение анализа | 712 RPS | 760+ RPS |
| Fair Play | 0,42 RPS | - |

Нагрузка на `api.chess.example` составляет около **2,14 тыс. RPS** в среднем без учёта игровых событий. Основная нагрузка на игровые регионы - **28,49 тыс. ходов/с** в среднем.

Chess.com не публикует DAU по регионам, поэтому точное распределение RPS между ДЦ не рассчитывается.

Все API-запросы направляются в Virginia. Игровая нагрузка распределяется матчмейкером между региональными игровыми кластерами.

### 3.5. Размещение данных

Постоянные данные пользователей, рейтингов и HOT-партий хранятся в Virginia. Каждый игровой регион независимо хранит рабочее состояние в Redis и фиксирует подтверждённые ходы в **региональной Kafka**.

```text
Game service → regional Kafka (game.moves)
             → Regional Relay → Kafka Virginia (game.finished)
             → Persistence Worker → PostgreSQL HOT
             → события для рейтинга, истории, архива и анализа
```

Regional Relay пересылает окончание партии после фиксации в региональном журнале. Если Virginia временно недоступна, завершённые партии остаются в региональном журнале до восстановления доставки.

В Virginia обрабатывается около **356 завершённых партий/с** в среднем и **380+/с** в пике. При `≈2,5 КБ` на событие входящий поток составляет `≈0,89–0,95 МБ/с` без репликации. Обработчики допускают повторную доставку и используют `game_id` для исключения дублей.

### 3.6. Anycast

Anycast не используется. API имеет единую точку входа в Virginia, а конкретный игровой регион выбирается матчмейкером. Игровое WebSocket-соединение после начала партии привязано к конкретному региону.

## 4. Локальная балансировка нагрузки

### 4.1. Внешняя и внутренняя балансировка

**В каждом из пяти регионов** один внешний AWS Network Load Balancer (L4) принимает TCP:443 и распределяет соединения между тремя активными NGINX L7 (по одному в AZ-A/B/C). NLB проверяет доступность NGINX; включена межзонная балансировка (`cross-zone`). TLS передаётся до NGINX, где расшифровываются HTTPS и WSS [[27]](#source27).

NGINX маршрутизирует запросы по домену и URL:

- В Virginia: `api.chess.example` → доступный **API Gateway**; `game-virginia.chess.example` → игровой контур.
- В Frankfurt, Mumbai, Singapore и São Paulo: `game-{region}.chess.example` → игровой контур.

**Внутренняя балансировка API в Virginia.** API Gateway определяет нужный микросервис. Отдельный **Internal AWS NLB (L4)** имеет TCP-listener/target group для каждого типа сервиса и выбирает доступный экземпляр Auth, Matchmaking, Fair Play или History/Analysis среди AZ [[28]](#source28). Kubernetes запускает экземпляры; AWS Load Balancer Controller обновляет их IP в target groups.

```text
HTTPS → внешний NLB → NGINX → API Gateway × N
                                       → внутренний NLB → Auth / Matchmaking /
                                          Fair Play / History × N
WSS   → внешний NLB → NGINX → Game Owner Lookup → Game service
```

Для WSS NGINX по `game_id` запрашивает **Game Owner Lookup**: он находит действующий Game service через `GAME_OWNER` (Redis). Оба игрока могут подключаться через разные NGINX/AZ, но попадают к одному владельцу партии. Lookup вызывается **при подключении**, а не на каждом ходе; право записи защищается fencing (п. 5.3). NGINX поддерживает проксирование WebSocket после HTTP Upgrade [[29]](#source29).

JWT проверяется API Gateway локально по кешу публичных ключей; Auth вызывается при входе и обновлении токена. Повторные операции создания матча/жалобы защищены идемпотентным ключом. Внутренний L4 распределяет **соединения**, поэтому долгоживущие HTTP/2-подключения и равномерность нагрузки проверяются отдельно.

### 4.2. TLS termination и нагрузка

TLS завершается на NGINX; внешний NLB работает в режиме TCP passthrough. HTTP RPS, новые TLS-соединения и одновременно открытые WSS учитываются отдельно: **число запросов не равно числу TLS-handshakes** из-за повторного использования HTTP-соединений.

Средний API-трафик по п. 3.4 — около 2,14 тыс. RPS. Для игр расчётный пик — 30 400+ ходов/с по всем регионам. Производительность NGINX проверяется измерением новых подключений/с, открытых WSS, throughput и p95/p99 задержек, включая потерю одной AZ; опубликованный SSL-тест [[10]](#source10) используется лишь как ориентир.

### 4.3. Отказоустойчивость

Все **три NGINX в регионе работают активно**: 5 × 3 = **15 экземпляров**. AWS NLB сам резервирован между AZ и исключает неисправные NGINX; Internal NLB аналогично исключает отказавшие API-экземпляры.

После потери одной AZ две оставшиеся должны выдерживать всю пиковую нагрузку региона — для этого закладывается резерв мощности и проводится отказный нагрузочный тест. Потерянные WSS переподключаются по прежнему домену, Game service восстанавливает партию из регионального журнала Kafka. Управляемая межзонная балансировка NLB и межзонный трафик учитываются в расходах [[30]](#source30).

# 5. Логическая схема базы данных

В разделе описываются логические сущности и потоки данных без привязки к конкретной СУБД, схеме шардинга и физическому размещению.

## 5.1. Идентификаторы

Автоинкрементные идентификаторы не используются для сущностей, которые потенциально создаются на разных узлах.

Независимые шарды могут генерировать пересекающиеся последовательности, а единый центральный sequence создаёт дополнительную точку синхронизации.

Для `user_id`, `game_id`, `report_id` и `server_id` используется 64-битный распределённый идентификатор:

```text
timestamp | worker_id | sequence
```

Размер идентификатора — `8 Б`.

Он генерируется без обращения к центральной БД, уникален между узлами, приблизительно сортируется по времени создания и занимает в два раза меньше места, чем бинарный UUID (`16 Б`).

## 5.3. Хранение ходов и состояния активной партии

Игровой сервер проверяет ход, его порядковый номер и актуальность владельца партии. **Прежде чем подтвердить ход игрокам, он фиксирует событие в региональной Kafka** (`game.moves`). Это долговечный журнал, размещённый в трёх AZ. Redis содержит быстрое рабочее представление того же состояния.

```text
WS game.move → Game service → Kafka game.moves (подтверждение)
                               ↓
                         Redis GAME_MOVE / GAME_STATE
                               ↓
                         ответ двум игрокам
```

Событие содержит `game_id`, номер полухода, ход, состояние часов и версию владельца. Повтор той же команды не создаёт второй ход. События одной партии направляются в одну партицию Kafka по `game_id`, поэтому их порядок сохраняется.

`GAME_STATE` хранит snapshot позиции и `snapshot_sequence`, а `GAME_MOVE` — не включённый в snapshot хвост. Каждые **10 полуходов** Redis атомарно обновляет snapshot и удаляет уже применённый хвост. После сбоя данные можно восстановить из snapshot и недостающих событий журнала; Redis не является единственным источником истины. Для длительного восстановления периодические контрольные точки записываются также в отдельный компактируемый topic `game.checkpoints`.

**Переключение Game service.** За каждой партицией журнала закреплён один действующий игровой обработчик. Назначение определяется через Kafka consumer group; для записи используется транзакционный producer со стабильным `transactional.id` на партицию. При смене владельца новый producer блокирует предыдущий механизмом fencing. До завершения восстановления последовательности ходов партия не принимает новые подтверждаемые действия. Номера полуходов и идентификаторы команд позволяют распознать повторную доставку. Ответ игрокам отправляется только после успешной фиксации события; корректность протокола проверяется тестами с остановкой процесса и сетевым разделением [[20]](#source20), [[26]](#source26).

**Завершение партии.** Финальное событие содержит полный результат и PGN либо данные для их восстановления. Regional Relay пересылает `game.finished` в Virginia и повторяет отправку при сбое сети. Временное состояние Redis удаляется после подтверждения сохранения в Virginia. Для Kafka применяется ограниченный срок хранения журнала, но только при наличии долговечных контрольных точек: итоговая точка завершённой партии удерживается до успешной доставки в Virginia.

## 5.4. Реестр игровых серверов

`GAME_SERVER` содержит текущее состояние игровых узлов:

| Поле | Назначение |
| --- | --- |
| `server_id` | глобальный идентификатор узла |
| `region` | игровой регион |
| `endpoint` | внутренний адрес |
| `healthy` | допускается ли узел к новым подключениям |
| `active_games` | число активных партий |
| `capacity` | расчётная вместимость |
| `last_heartbeat` | время последнего heartbeat |

Matchmaking использует состояние серверов для выбора игрового региона. `GAME_OWNER[partition_id]` в региональном Redis хранит текущий `server_id` владельца партиции `game.moves`. **Game Owner Lookup** запрашивает его при установлении WSS, после чего NGINX проксирует соединение на нужный Game service. Право подтверждать ход проверяется Kafka fencing, а не только наличием маршрута в Redis.

Если heartbeat не поступает дольше заданного timeout, сервер считается `unhealthy`.

# 6. Физическая схема базы данных

В проекте используются два класса постоянного хранения:

- **OLTP-хранилище** — для данных, к которым нужен быстрый доступ и частые точечные чтения/изменения;
- **OLAP-хранилище** — для большого архива завершённых партий и исторических запросов.

Такое разделение позволяет не держать все `30+ млрд` партий в дорогом быстром OLTP-хранилище.

Для проектируемой системы принимается следующая политика:

```text
последние 30 суток -> PostgreSQL
вся история        -> ClickHouse
```

ClickHouse получает завершённые партии асинхронно сразу после их появления, поэтому перенос партии в архив не требует отдельной тяжёлой миграции через месяц.

После истечения 30 суток данные удаляются из PostgreSQL только после проверки полноты архива в ClickHouse (п. 6.2).

Если у пользователя за последние 30 суток меньше 20 партий, API получает недостающие строки истории из ClickHouse. Таким образом, интерфейс всегда может показать последние 20 партий, но полная запись старой партии не обязана находиться в PostgreSQL.

PostgreSQL используется как реляционная OLTP-СУБД, Redis - как in-memory хранилище, ClickHouse - как аналитическая колоночная СУБД, Kafka - как потоковая система.

## 6.2. Горячее и архивное хранение партий

Средний прирост основных данных:

```text
GAME     ≈ 71,2 ГБ/сутки
ANALYSIS ≈ 76,9 ГБ/сутки

Итого    ≈ 148,1 ГБ/сутки
```

За 30 суток:

```text
148,1 × 30 ≈ 4,44 ТБ
```

Следовательно, в PostgreSQL не требуется хранить весь архив объёмом `≈144,45 ТБ`.

В нём находится только горячий набор данных порядка:

```text
≈4,44 ТБ данных GAME_HOT и ANALYSIS_HOT
+ USER_GAME_HISTORY_HOT, индексы, WAL и служебные данные
```

`GAME_HOT`, `ANALYSIS_HOT` и `USER_GAME_HISTORY_HOT` на каждом физическом шарде секционируются по `ended_at` на **дневные разделы (UTC)**. Разделы создаются заранее; `DEFAULT`-раздел не используется. Такой способ позволяет удалять старые данные без массового `DELETE` и последующего `VACUUM` [[13]](#source13).

**Удаление старых данных** выполняет `Retention Worker` (Kubernetes CronJob) один раз в сутки:

1. Выбирает завершённые дневные разделы старше 30 суток и закрывает их для новых HOT-записей; запоздавшие результаты направляются в ClickHouse.
2. Дожидается завершения записи и сверяет число и контрольные суммы партий, истории и готовых анализов с ClickHouse. Проверяет, что события дня обработаны и нет незавершённых архивных задач; статус фиксируется в основном PostgreSQL (`ARCHIVE_PARTITION_STATUS`: таблица, шард, день, число записей, контрольная сумма, статус).
3. Отсоединяет подтверждённый раздел через `DETACH PARTITION ... CONCURRENTLY`, затем удаляет отсоединённую таблицу [[13]](#source13), [[14]](#source14).

Операция выполняется для всех трёх HOT-таблиц и восьми шардов (до **24 дневных разделов в сутки**). В штатном режиме освобождается около `148,1 ГБ/сутки` логических данных `GAME_HOT + ANALYSIS_HOT` без истории, индексов и реплик. При отсутствии подтверждения архива, расхождении данных или задержке обработчиков раздел **не удаляется**: срок горячего хранения временно увеличивается. Повторное выполнение задачи безопасно; параллельная очистка одного раздела запрещена.

## 6.3. Шардирование PostgreSQL

Для горячего хранилища принимается `8` групп PostgreSQL.

При равномерном распределении:

```text
4,44 ТБ / 8 ≈ 0,56 ТБ логических данных на шард
```

Это оценка только `GAME_HOT + ANALYSIS_HOT`, без истории, индексов и WAL. Даже с индексами и запасом это значительно проще размещать на сервере, чем весь архив.

Каждая группа содержит **1 основной узел и 2 реплики в разных AZ**. CloudNativePG управляет переключением; транзакция подтверждается после получения WAL как минимум одной синхронной репликой [[15]](#source15), [[16]](#source16).

```text
HOT PostgreSQL:  8 × 3 = 24 экземпляра
Основной PostgreSQL:      3 экземпляра
Итого:                   27 экземпляров
```

Для трёх копий основных горячих данных требуется приблизительно `4,44 × 3 = 13,32 ТБ` дискового пространства без индексов, истории, WAL и запаса. Число физических серверов определяется отдельно.

### Виртуальные сегменты

Прямое правило вида `shard = game_id % 8` не используется: при изменении количества физических шардов оно потребовало бы массового перераспределения данных.

Вместо этого применяется `1024` виртуальных сегмента:

```text
bucket_id = hash64(game_id) mod 1024
SHARD_MAP[bucket_id] -> physical_shard
```

При 8 шардах приходится по `128` виртуальных сегментов на шард. `SHARD_MAP` хранится в основном PostgreSQL и кешируется маршрутизатором.

`GAME_HOT` и `ANALYSIS_HOT` размещаются по `game_id` на одном шарде. `USER_GAME_HISTORY_HOT` распределяется независимо, по `hash64(user_id) mod 1024`, чтобы история пользователя не требовала обхода всех шардов. Для двух семейств используются отдельные отображения виртуальных сегментов на те же восемь групп PostgreSQL.

## 6.4. Таблицы PostgreSQL

### USER

```text
PK (user_id)
UNIQUE (username)
INDEX (country)
```

`avatar` содержит только ключ объекта в Ceph RGW.

### RATING

```text
PK (user_id, rating_type)
```

Оба рейтинга одной партии обновляются одной транзакцией. `RATING_APPLIED_GAME (game_id PK)` фиксирует применённые результаты, исключая повторный пересчёт при повторной доставке события.

### FAIR_PLAY_REPORT

```text
PK (report_id)
INDEX (game_id)
INDEX (reporter_user_id, created_at DESC)
INDEX (status, created_at)
```

### GAME_HOT

```text
PK (game_id, ended_at)
INDEX (ended_at)
```

Таблица секционируется по `ended_at` на дневные разделы (UTC). В состав физического первичного ключа включается ключ секционирования — требование PostgreSQL [[13]](#source13).

### ANALYSIS_HOT

```text
PK (game_id, ended_at)
```

Хранится на том же шарде, что и `GAME_HOT`. Для секционирования используется `ended_at` исходной партии, а не время готовности анализа. Запоздавший анализ старой партии сохраняется непосредственно в ClickHouse.

### USER_GAME_HISTORY_HOT

```text
PK (user_id, ended_at, game_id)
INDEX (user_id, ended_at DESC)
INDEX (user_id, opponent_user_id, ended_at DESC)
INDEX (user_id, game_type, time_control, ended_at DESC)
```

Секционируется по `ended_at` на дневные разделы. На одну партию создаются две записи: для белых и для чёрных.

```text
356 партий/с × 2 ≈ 712 inserts/с
```

Уникальность `game_id` между разными дневными разделами обеспечивается идемпотентностью обработчика записи; составной физический PK сам по себе не обеспечивает глобальную уникальность одного `game_id`.

### OUTBOX

В том же HOT-шарде, что `GAME_HOT`, хранится небольшая таблица `OUTBOX (event_id PK, game_id, event_type, payload, published_at)`. Сохранение партии и запись `game.persisted` в OUTBOX выполняются **одной транзакцией PostgreSQL**. Outbox Relay передаёт событие в Kafka с возможностью повторной отправки.

`USER_GAME_HISTORY_HOT` лежит на шарде пользователя, поэтому создаётся отдельно через `History Worker`, а не в одной транзакции с `GAME_HOT`. Он делает по одной идемпотентной записи каждому игроку.

## 6.5. Архив в ClickHouse

ClickHouse используется для хранения данных, которые после завершения партии практически не изменяются.

Используются три основные таблицы.

### GAME_ARCHIVE

Организация:

```text
PARTITION BY toYYYYMM(ended_at)
ORDER BY game_id
```

### ANALYSIS_ARCHIVE

Основной поиск выполняется по `game_id`.

### USER_GAME_HISTORY_ARCHIVE

Организация данных:

```text
PARTITION BY toYYYYMM(ended_at)
ORDER BY (user_id, ended_at, game_id)
```

Такой порядок подходит под запрос:

```text
история пользователя
+ период
+ соперник
+ тип партии
```

ClickHouse хорошо подходит для этой части системы, потому что архив:

- очень большой;
- в основном дописывается;
- почти не изменяется;
- читается по большим историческим диапазонам;
- используется для фильтрации и аналитики.

## 6.6. GAME_SERVER и matchmaking

Реестр игровых серверов хранится в Redis: `gameserver:{server_id}`

Поля:

```text
region
endpoint
healthy
active_games
capacity
last_heartbeat
```

Heartbeat обновляет запись и срок жизни. Если heartbeat перестал приходить, запись истекает, и сервер перестаёт считаться доступным.

Matchmaking использует этот реестр для оценки загрузки игрового региона. При переподключении NGINX по `game_id` определяет партицию `game.moves` и читает её текущего владельца из `GAME_OWNER`; устаревший маршрут не даёт права на запись.

Когорты рассчитываются отдельно для каждого сочетания:

```text
game_type + time_control
```

Общий поток данных:

```text
USER_GAME_HISTORY_ARCHIVE
        ↓
ClickHouse
        ↓
агрегация активных игроков и рейтингов
        ↓
расчёт границ когорт
        ↓
MATCHMAKING_COHORT_CONFIG
        ↓
PostgreSQL
        ↓
локальный кеш matchmaking
        ↓
Redis MATCHMAKING_QUEUE
```

Итоговая конфигурация записывается в основной PostgreSQL:

```text
MATCHMAKING_COHORT_CONFIG
```

Структура:

```text
version
game_type
time_control
cohort_id
rating_min
rating_max
active_players
calculated_at
```

Первичный ключ:

```text
(version, game_type, time_control, cohort_id)
```

## 6.7. Kafka

**Региональная Kafka** хранит `game.moves` и компактируемый topic контрольных точек `game.checkpoints` во всех пяти игровых регионах. Это позволяет ограничивать срок хранения старых ходов, не теряя восстановление длительных и ещё не доставленных партий. Game service подтверждает ход только после записи в журнал. Regional Relay передаёт финальное `game.finished` в Virginia; при разрыве связи событие остаётся в регионе для повторной доставки.

В **Kafka Virginia** используются отдельные topics и consumer groups:

| Topic | Кто публикует | Кто читает |
| --- | --- | --- |
| `game.finished` | Regional Relay | Persistence Worker |
| `game.persisted` | Outbox Relay | Rating, History, Archive Workers; Analysis Dispatcher (независимые группы) |
| `analysis.tasks` | Analysis Dispatcher | Stockfish workers |
| `analysis.finished` | Stockfish workers | Analysis Persistence Worker |
| `analysis.persisted` | Outbox Relay | Archive Worker для результата анализа |

Archive Worker записывает `GAME_ARCHIVE` и две строки `USER_GAME_HISTORY_ARCHIVE`; History Worker формирует две записи `USER_GAME_HISTORY_HOT` на шардах пользователей. Persistence Worker сначала сохраняет `GAME_HOT` и OUTBOX в одной транзакции. Затем `game.persisted` независимо запускает пересчёт рейтинга, создание двух записей истории, архивирование и анализ. Анализ сохраняется в `ANALYSIS_HOT` на шарде партии; при устаревшем дне сразу в ClickHouse. Если записан в HOT, событие `analysis.persisted` запускает архивирование анализа. Повторная доставка не должна создавать дубликаты.

Оба типа кластеров Kafka разнесены по трём AZ: **минимум три брокера на регион**, `replication.factor=3`, `min.insync.replicas=2`, у producers `acks=all`, небезопасное назначение несинхронной реплики выключено. Для продюсеров ходов дополнительно используется транзакционное fencing. Всего работают **шесть независимых Kafka-кластеров**: пять региональных и один центральный в Virginia. Минимальная конфигурация — **18 брокеров** (`6 × 3`) и **18 выделенных KRaft controllers** (`6 × 3`), по одному брокеру и контроллеру каждого кластера в AZ. Количество партиций и требуемая производительность брокеров определяются нагрузочными испытаниями [[25]](#source25), [[26]](#source26).

Kafka — долговечный буфер, но не замена PostgreSQL и ClickHouse. Транзакции и OUTBOX нужны для надёжной передачи событий между разными хранилищами.

## 6.8. Ceph RGW и облачное S3

**Ceph RGW** — наше S3-совместимое объектное хранилище в Virginia. В нём хранятся **аватары пользователей** и **локальные резервные копии** основного PostgreSQL, восьми HOT-шардов и ClickHouse. Рабочие таблицы PostgreSQL и ClickHouse в Ceph не переносятся [[12]](#source12).

Шлюзы RGW и дисковые узлы Ceph распределены по трём AZ; данные реплицируются по независимым отказным доменам через CRUSH. Для Ceph предусмотрены три MON (кворум) и несколько шлюзов RGW [[23]](#source23).

**Backup Replicator** асинхронно переносит проверенные резервные наборы и необходимые WAL-файлы из Ceph в **Amazon S3 другого региона и отдельного AWS-аккаунта**. В S3 включены Versioning, Object Lock и отдельные права восстановления [[24]](#source24). Копирование не влияет на обработку игровых ходов. Для аватаров также создаётся независимая облачная копия.

Репликация Ceph защищает от отказа узла/AZ, а независимый S3 — от потери Virginia или ошибочного удаления. Это два разных механизма защиты.

## 6.9. Репликация

Основной PostgreSQL и каждый из восьми HOT-шардов используют **1 primary + 2 replica в разных AZ**. CloudNativePG выполняет безопасное переключение, запись требует подтверждения одной синхронной реплики. Всего **27 экземпляров PostgreSQL**, как рассчитано в п. 6.3 [[15]](#source15), [[16]](#source16).

Используются **шесть независимых Redis Cluster**: центральный кластер Virginia хранит `MATCHMAKING_QUEUE` и `GAME_SERVER`, а пять игровых кластеров, включая отдельный игровой кластер Virginia, хранят `GAME_STATE`, `GAME_MOVE` и `GAME_OWNER`. Каждый кластер содержит **3 master + 3 replica** с размещением пар master и replica в разных AZ. Всего предусмотрено **36 экземпляров Redis**. Репликация Redis асинхронная; подтверждённые ходы сохраняются в региональном Kafka-журнале [[18]](#source18).

ClickHouse хранит минимум две реплики каждого архивного шарда и использует три узла Keeper. Региональная и центральная Kafka реплицируют сообщения между тремя AZ (п. 6.7). Ceph хранит реплики объектов в разных AZ (п. 6.8).

## 6.11. Резервное копирование

**PostgreSQL.** Для основного кластера и восьми HOT-шардов выполняются физические base backup и непрерывное архивирование WAL через CloudNativePG/Barman Cloud Plugin. Копии сохраняются в Ceph RGW; Backup Replicator передаёт завершённые наборы и нужную WAL-цепочку в Amazon S3. Это позволяет выполнять Point-in-Time Recovery (PITR) [[17]](#source17), [[31]](#source31).

**ClickHouse.** Полные и инкрементальные резервные копии архива и метаданных сохраняются в Ceph, затем копируются в Amazon S3. Наличие реплик ClickHouse не заменяет backup [[19]](#source19).

**Аватары.** Основные объекты размещены в Ceph, резервная версия — в Amazon S3.

**Redis и Kafka.** Redis использует реплики и AOF; подтверждённые ходы восстанавливаются по региональному Kafka-журналу. Kafka реплицирует сообщения между AZ, региональные завершения удерживаются до подтверждённой доставки в Virginia.

**Проверка.** Контролируются успешность копирования, полнота WAL и резервных наборов, сроки хранения и регулярное тестовое восстановление из Ceph и Amazon S3. Сбой облака не останавливает игру; копирование повторяется после восстановления доступа.

# 7. Алгоритмы

Основной нетривиальный алгоритм проекта — подбор соперника и выбор игрового дата-центра.

Матчмейкинг должен одновременно учитывать:

- настройки партии;
- рейтинг игроков;
- время ожидания;
- задержку обоих игроков до пяти игровых ДЦ;
- доступность и текущую загрузку регионов.

Он работает в Virginia вместе с основным API.

---

## 7.1. Разбиение игроков на рейтинговые когорты

Полный перебор всех пользователей очереди при каждом запросе не требуется.

В ClickHouse периодически рассчитывается распределение рейтинга активных игроков отдельно для каждого типа партии: `game_type + time_control`.

На основе распределения формируются **рейтинговые когорты**. Целевой размер одной когорты принимается в диапазоне:

```text
10 000 – 50 000 активных игроков
```

Когорта является логической группой матчмейкинга и не является `PARTITION` таблицы ClickHouse. Границы кагорты имеют такой разброс, так как рейтинг близок к нормальному распределнию.

Границы когорт выбираются по распределению игроков, поэтому они необязательно имеют одинаковую ширину по рейтингу. В области с большим количеством игроков диапазон рейтинга получается уже, в области с меньшим количеством игроков - шире.

Периодическое обновление выполняется отдельно:

```text
ClickHouse
    ↓ cron
расчёт распределения рейтингов
    ↓
новая версия MATCHMAKING_COHORT_CONFIG
    ↓
PostgreSQL
    ↓
локальный кеш matchmaking
```

Тяжёлая аналитическая часть полностью вынесена из поиска соперника. ClickHouse используется для периодического расчёта статистики. Онлайн-поиск пары выполняется в Redis и не требует запроса в ClickHouse на каждый matchmaking-запрос.

---

## 7.2. Постановка игрока в очередь

Перед началом поиска клиент измеряет RTT до пяти игровых регионов. Для каждого региона выполняется несколько измерений, после чего клиент передаёт устойчивое значение задержки (медиану).

Matchmaking определяет рейтинговую когорту игрока и помещает его в соответствующую очередь Redis. Внутри когорты игроки индексируются по рейтингу, поэтому для поиска кандидата не требуется последовательно просматривать всю очередь.

---

## 7.3. Поиск соперника

Первоначально поиск выполняется только среди игроков:

```text
одинаковый game_type + одинаковый time_control + та же рейтинговая когорта
```

Для игрока `A` определяется допустимое отклонение рейтинга: `Δrating = f(wait_time)`

Чем дольше игрок находится в очереди, тем шире разрешённый диапазон рейтинга.

В начале поиска: `ratingA - Δrating <= ratingB <= ratingA + Δrating`

Если подходящего игрока в текущей когорте нет, после увеличения времени ожидания поиск расширяется на соседние когорты.

Это позволяет одновременно:

- быстро находить соперника в популярных рейтинговых диапазонах;
- не оставлять игроков редких рейтингов без пары;
- не выполнять полный перебор всей очереди.

Из нескольких допустимых кандидатов приоритет определяется следующим образом:

1. минимальная разница рейтинга;
2. большее время ожидания;
3. лучшее качество общего игрового региона.

---

## 7.4. Проверка совместимости по регионам

После подбора противника необходимо проверить, существует ли игровой регион с приемлемой задержкой для обоих игроков.

Для каждого доступного региона `r` известны `latencyA[r] + latencyB[r]`

Из `GAME_SERVER` также известно, доступен ли регион и насколько он загружен. Недоступные регионы сразу исключаются.

Для оставшихся регионов основным показателем является:

```text
region_latency(r) =
max(latencyA[r], latencyB[r])
```

То есть оптимизируется задержка игрока, находящегося в худшем положении.Использование максимума, а не только средней задержки, не позволяет выбрать регион, удобный одному игроку и неприемлемый другому.

При одинаковом значении `max latency` используются дополнительные критерии:

```text
1. меньшая средняя задержка двух игроков;
2. меньшая загрузка региона.
```

Итоговый порядок выбора региона:

```text
минимальный max latency
        ↓
минимальный average latency
        ↓
минимальная загрузка
```

Такой порядок не требует вводить весовые коэффициенты. Если минимальная задержка превышает допустимый для игры порог, игроки не объединяются и продолжают поиск.

---

## 7.5. Выбор игрового сервера

Matchmaking выбирает **регион**, затем оба клиента получают `game_id` и адрес `game-{region}.chess.example`.

При установлении WSS **Game Owner Lookup** вычисляет по `game_id` партицию `game.moves` и получает адрес текущего Game service из `GAME_OWNER` (региональный Redis). NGINX проксирует оба подключения на этого владельца независимо от входной AZ. Каждая партиция назначена одному владельцу через Kafka consumer group; маршрут обновляется при смене экземпляра.

Новый владелец восстанавливает последний подтверждённый ход из Kafka и обновляет маршрут в Redis. При повторном подключении клиент попадает к текущему владельцу. Транзакционное fencing Kafka не позволяет прежнему владельцу подтвердить новые записи после переключения (п. 5.3).

Серверы без heartbeat или с `healthy=false` исключаются из новых назначений. Matchmaking не выбирает конкретный экземпляр Game service — только игровой регион.

## 7.6. Полный алгоритм matchmaking

```text
1. Клиент измеряет latency до пяти ДЦ.

2. Клиент отправляет:
      user_id
      game_type
      time_control
      rating
      latency_by_region

3. Matchmaking:
      читает активную конфигурацию когорт из локального кеша;
      определяет cohort_id по game_type, time_control и rating;
      помещает игрока в соответствующую очередь Redis.

4. Ищется кандидат:
      с теми же настройками партии;
      сначала в той же когорте;
      в допустимом диапазоне рейтинга.

5. Для каждой потенциальной пары:
      берутся latency обоих игроков;
      вычисляется лучший общий регион.

6. Если существует подходящая пара:
      выбирается кандидат с минимальной разницей рейтинга;
      при равенстве учитывается время ожидания
      и качество общего региона.

7. Matchmaking создаёт game_id.

8. Игроки удаляются из очереди.

9. Обоим игрокам возвращаются:
      game_id
      цвет фигур
      данные соперника
      выбранный game-{region}.chess.example

10. Оба клиента подключаются к выбранному игровому ДЦ.
```

# 8. Технологии

Выбор технологий определяется профилем нагрузки отдельных компонентов системы. Для транзакционных данных, активных партий, архива, очередей и файлов используются разные специализированные решения.

| Технология | Область применения | Мотивация |
| --- | --- | --- |
| **NGINX** | Внешняя L7-балансировка HTTP/WSS, TLS termination | По три активных экземпляра на регион, по одному в каждой AZ |
| **AWS NLB (внешний L4)** | Входящий трафик между AZ каждого региона | TCP passthrough к трём активным NGINX; health checks и cross-zone routing |
| **AWS NLB (внутренний L4)** | API Gateway → экземпляры Auth, Matchmaking, Fair Play, History | Отдельные target groups; выбор здорового backend по TCP, независимо от Kubernetes Service |
| **AWS Load Balancer Controller** | Регистрация адресов Pod'ов в target groups NLB | Автоматически обновляет backend-экземпляры при масштабировании Kubernetes |
| **PostgreSQL** | `USER`, `RATING`, `FAIR_PLAY_REPORT`, горячие `GAME` и `ANALYSIS`, конфигурация когорт | Нужны транзакции, индексы, точечные чтения и строгая консистентность; объём горячих данных ограничен 30 сутками |
| **PgBouncer** | Пул соединений с PostgreSQL | Уменьшает количество физических соединений с БД и снижает накладные расходы на их создание |
| **Redis Cluster** | `MATCHMAKING_QUEUE`, `GAME_SERVER`, региональные `GAME_STATE` и `GAME_MOVE` | Низкая задержка и высокая частота операций; кластер позволяет распределять нагрузку и хранить состояние активных партий рядом с game-server |
| **Redis AOF** | Локальное восстановление `GAME_STATE` / `GAME_MOVE` | Ускоряет восстановление, но сохранность подтверждённых ходов обеспечивает региональный журнал Kafka |
| **ClickHouse** | Полный архив партий и анализов, история пользователей, расчёт рейтинговых когорт | Подходит для большого объёма почти неизменяемых данных, исторических запросов и пакетных аналитических агрегаций |
| **Kafka** | Региональный `game.moves` и центральные topics завершения/анализа | Долговечная фиксация ходов, независимые группы потребителей и повторная обработка |
| **Ceph RGW** | Аватары, локальные резервные копии | Масштабируемое S3-совместимое хранилище, распределённое между AZ |
| **Amazon S3** | Независимые резервные копии вне Virginia | Защита от потери региона и ошибочного удаления через Versioning / Object Lock |
| **Stockfish** | Анализ завершённых шахматных партий | Специализированный шахматный движок; анализ выполняется асинхронно и не блокирует завершение партии |
| **REST / HTTP(S)** | Клиентское API: matchmaking, история, анализ, Fair Play | Простой и явный интерфейс для синхронных запросов, где клиент ожидает ответ |
| **WebSocket / WSS** | Передача ходов и событий активной партии | Постоянное двунаправленное соединение уменьшает накладные расходы и подходит для realtime-взаимодействия |
| **TLS** | Защита внешнего HTTP и WebSocket-трафика | Шифрование клиентского трафика; TLS завершается на NGINX |
| **64-bit Snowflake-like ID** | `user_id`, `game_id`, `report_id`, `server_id` | Генерируется распределённо без общего auto-increment sequence и занимает `8 Б` вместо `16 Б` бинарного UUID |
| **Kubernetes** | API, Game service, Worker'ы и плановые задачи | Перезапуск экземпляров, несколько реплик, распределение между узлами и выполнение CronJob |
| **CloudNativePG** | Основной и HOT PostgreSQL | Синхронная репликация, автоматическое переключение основного узла, управление точкой подключения и восстановлением |
| **ClickHouse Keeper** | Реплицированный ClickHouse | Координация реплик и метаданных архива |

Архитектура использует PostgreSQL для OLTP, ClickHouse для архива и аналитики, Redis для горячего состояния, Kafka для событий и Ceph/S3 для объектов и резервных копий. Kubernetes распределяет экземпляры сервисов между AZ.

# 9. Обеспечение надёжности

В каждом регионе три AZ. Отказ одной зоны не должен останавливать регион: сервисы распределены по AZ, а БД и журналы имеют реплики. Kubernetes восстанавливает процессы; **данные защищают репликация и резервные копии**.

| Компонент | Резервирование | При отказе |
| --- | --- | --- |
| **Внешний NLB / NGINX** | 1 управляемый NLB + 3 активных NGINX на регион (по AZ) | NLB выбирает доступный NGINX; WSS переподключаются |
| **Внутренний NLB Virginia** | Управляемый L4, отдельные target groups для API-микросервисов | Исключает недоступные экземпляры |
| **API и микросервисы** | Не менее 3 экземпляров Kubernetes, распределены по AZ | Внутренний NLB выбирает доступный экземпляр |
| **Game service** | Экземпляры во всех AZ, владелец партии закреплён за партицией Kafka | Новый владелец восстанавливает ходы; старый блокируется fencing |
| **Workers** | Несколько экземпляров Kubernetes; CronJob с запретом параллельных запусков | Kafka повторно доставляет события, идемпотентная запись исключает дубли |
| **PostgreSQL / PgBouncer** | 1 primary + 2 replica на кластер, CloudNativePG; PgBouncer по AZ | Безопасный failover и переподключение; всего 27 PostgreSQL |
| **Redis** | 3 master + 3 replica на кластер, AOF | Реплика становится master; ходы сверяются с региональной Kafka |
| **Kafka** | По 3 брокера на кластер, реплики в разных AZ | После потери одной AZ журнал остаётся доступным при наличии кворума |
| **ClickHouse** | 2 реплики на архивный шард, 3 Keeper | Чтения и архивирование продолжаются на доступных репликах |
| **Ceph / Amazon S3** | Ceph: аватары и backup PostgreSQL/ClickHouse по AZ; S3 другого региона: независимые копии | Восстановление из Ceph или облака |

## Сценарии восстановления

**Отказ AZ или PostgreSQL.** NLB исключает недоступный NGINX; CloudNativePG переключает primary на подходящую реплику. Приложения переподключаются, а повторные операции записи выполняют с контролем идемпотентности.

**Отказ Game service или Redis.** Игрок переподключается. Новый Game service восстанавливает подтверждённые ходы из региональной Kafka, а Redis — рабочее состояние. Если журнал потерял кворум, новые ходы не подтверждаются.

**Недоступность ClickHouse.** Игры и HOT-записи продолжаются. Archive Worker повторяет доставку; Retention Worker не удаляет суточные разделы до проверки архива.

**Отказ Virginia.** Уже начатые партии могут продолжаться в игровых регионах. Regional Relay удерживает завершения до восстановления связи. Новые матчи, авторизация и история временно ограничены; автоматический перенос всего API в другой регион не предусмотрен.

## Graceful degradation и graceful shutdown

При перегрузке Stockfish анализ ставится в очередь, но партии не замедляются. Если ClickHouse недоступен, пользователю показывается доступная HOT-история. Сбой облачного S3 не блокирует игру, но вызывает предупреждение о задержке резервного копирования.

При плановой остановке Game service перестаёт принимать новые партии, фиксирует принятые ходы, передаёт владение и предлагает клиентам переподключиться. Worker завершает текущую запись перед подтверждением сообщения Kafka. При инфраструктурном сбое, мешающем безопасно подтвердить ход, игра и её часы временно приостанавливаются, а не засчитывают поражение игроку.

Для проверки используются метрики `move_ack_p99`, время восстановления партии, `kafka_consumer_lag`, отставание реплик PostgreSQL, возраст неархивированных партий и успешность тестового восстановления из облака. Нагрузка проверяется также при отказе одной AZ и при кратковременном всплеске ×3 относительно расчётного пика.

# 10. Схема проекта

Архитектура показана в редактируемом файле [`architecture.drawio`](architecture.drawio) на трёх листах: **«Балансировка и AZ»**, **«События и Worker’ы»**, **«Хранение и резервные копии»**. Virginia совмещает API и игровой регион; остальные четыре региона обслуживают игровые WSS.

![Схема проекта: балансировка и AZ](architecture_balancing.png)

![Схема проекта: Kafka и Worker'ы](architecture_events.png)

![Схема проекта: Ceph и облачные резервные копии](architecture_backup.png)

## 10.1. Основные элементы

- **Внешний NLB → NGINX:** один региональный L4 и три активных L7 по AZ. NGINX различает HTTPS API и WSS Game.
- **API Gateway → внутренний NLB:** Virginia; внутренний L4 выбирает экземпляры Auth, Matchmaking, Fair Play и History/Analysis.
- **Game Owner Lookup → Game service:** оба WSS-соединения направляются к одному действующему владельцу партии независимо от входной AZ.
- **Redis / Kafka:** Redis хранит быстрое состояние, региональная Kafka — подтверждённые ходы и контрольные точки.
- **PostgreSQL / ClickHouse:** HOT за 30 суток и архив; Worker'ы обрабатывают независимые Kafka topics.
- **Ceph RGW → Backup Replicator → Amazon S3:** аватары и локальные backup в Ceph, независимые копии вне Virginia.

## 10.2. Основные потоки

1. **Поиск:** HTTPS → внешний NLB Virginia → NGINX → API Gateway → внутренний NLB → Matchmaking.
2. **Партия:** WSS → внешний NLB выбранного региона → NGINX → Game Owner Lookup → Game service → региональная Kafka и Redis.
3. **Завершение:** Regional Relay → `game.finished` (Virginia) → Persistence Worker → `GAME_HOT` + OUTBOX → `game.persisted` → Rating/History/Archive/Analysis.
4. **Анализ:** `analysis.tasks` → Stockfish → `analysis.finished` → Analysis Persistence Worker → `ANALYSIS_HOT` + OUTBOX → `analysis.persisted` → Archive Worker → ClickHouse.
5. **Резервирование:** backup PostgreSQL и ClickHouse → Ceph RGW → Backup Replicator → Amazon S3; аватары сохраняются в Ceph с облачной копией.

# 11. Список серверов и оценка стоимости

Для размещения выбран **Amazon Web Services (AWS)**: Virginia (`us-east-1`) — центральный API, базы данных и один из игровых регионов; Frankfurt, Mumbai, Singapore и São Paulo — игровые регионы. В каждом регионе используются три Availability Zones. Kubernetes развёрнут в **пяти кластерах Amazon EKS**, по одному на регион.

Это **предварительная конфигурация** для проверки нагрузкой. Цены приведены в долларах США по тарифам **Virginia**, Linux EC2 On-Demand, **730 часов в месяц**, без скидок. Фактические ставки в других регионах отличаются [[32]](#source32), [[33]](#source33).

**Распределение по AZ.** В каждом регионе размещаются три активных NGINX, шесть узлов Redis игрового кластера, три брокера и три контроллера региональной Kafka. В Virginia дополнительно находятся центральные Redis и Kafka, 27 экземпляров PostgreSQL, 12 ClickHouse и Ceph. Центральные кластеры Redis и Kafka физически отделены от игровых кластеров Virginia. Для каждого кластера PostgreSQL предусмотрены один Primary и две реплики в разных AZ. Отказ одной AZ должен покрываться ресурсами двух оставшихся.

Внешняя балансировка обеспечивается **пятью AWS NLB**, внутренняя балансировка API — **одним Internal NLB** в Virginia. Это управляемые сервисы AWS, в число EC2-серверов они не входят.

Число узлов **Stockfish (180)** показано как **сценарий**, а не как подтверждённая потребность: оно зависит от скорости движка при выбранной глубине анализа. Остальные количества также являются стартовым планом размещения и уточняются нагрузочным тестированием.

## 11.3. Дисковое пространство

| Хранилище | Выделенный объём |
| --- | ---: |
| PostgreSQL, включая реплики и запас | 42 ТБ |
| ClickHouse, включая реплики и запас | 432 ТБ |
| Ceph OSD (физический объём) | 900 ТБ |
| Kafka, все шесть кластеров | 51 ТБ |
| Redis AOF | 3,6 ТБ |
| Мониторинг и системные диски | 21 ТБ |
| **Итого EBS** | **≈1 450 ТБ** |

Для оценки весь выделенный объём посчитан как EBS `gp3` по цене **$0,08/ГБ·мес. в Virginia**. Это тарифная модель, а не готовый план размещения дисков: для Ceph предусмотрено несколько томов на OSD-узел; требуемая скорость I/O, дополнительные IOPS и пропускная способность оцениваются отдельно [[34]](#source34).

**Размер Ceph принципиален.** В РПЗ архив ClickHouse оценивается в `≈144,45 ТБ` логических данных. Ceph должен вместить как минимум одну полноценную резервную копию этого архива, резервные копии PostgreSQL и ближайшие инкрементальные изменения. При трёх копиях и 25% свободного пространства `900 / 3 × 0,75 ≈ 225 ТБ` доступно для размещения объектов. Это консервативная оценка без выигрыша от сжатия. Девять OSD-серверов получают по `100 ТБ` EBS каждый (несколько томов на сервер).

Amazon S3 в отдельном аккаунте и регионе (`us-east-2`, Ohio) используется для **независимых резервных копий**, а не как рабочая база данных. Для стартовой сметы принимаем `180 ТБ` облачного хранения, достаточные только для выбранного начального набора копий при принятых объёмах. Хранение нескольких полных поколений резервных копий потребует дополнительного пространства; его объём зависит от политики retention и сжатия.

Цены EC2 сверены для `us-east-1`, EBS — с тарифом gp3, S3 — с тарифными ступенями Standard, NLB и EKS — с базовой почасовой оплатой [[32]](#source32)–[[37]](#source37). Стоимость NLB **не включает NLCU**, а итоговая таблица не включает интернет-трафик, межзонную/межрегиональную передачу данных, запросы S3, CloudWatch, дополнительные IOPS, налоги и различия региональных тарифов.

**Допущение для Stockfish:** анализ каждой из 80 позиций партии требует `0,1 vCPU·с`. Тогда при пике `30 400 позиций/с` и выделении `28 vCPU` на сервер после потери одной AZ остаются `120 × 28 / 0,1 ≈ 33 600 позиций/с` расчётной мощности. Без измерения реального времени анализа это нельзя считать гарантированной пропускной способностью. При удвоении CPU-времени потребуется примерно вдвое больше вычислительных ресурсов.

Таким образом, **около $382 тыс./мес.** — стоимость перечисленных ресурсов по единым тарифам Virginia **при принятом сценарии Stockfish**, без переменных расходов. Для предварительного бюджета можно заложить **около $440 тыс./мес.** с 15% резервом, понимая, что реальные сетевые расходы и региональные тарифы необходимо рассчитать отдельно. Окончательная конфигурация определяется измерением Stockfish, сжатия ClickHouse и нагрузки при отказе AZ.
