# Текст защиты курсового проекта Highload Chess

## Слайд 1. Высоконагруженная платформа онлайн-шахмат

Здравствуйте. Представляю проект распределённой платформы онлайн-шахмат. Основная задача — обеспечить быструю обработку ходов, надёжное хранение партий и устойчивость к отказам. Покажу, как организована балансировка, резервирование и обработка событий, а затем обосную выбранные решения.

## Слайд 2. Разделение нагрузки на два контура

Я разделил нагрузку на два контура. Центральный API в Virginia обслуживает авторизацию, поиск соперника, историю и анализ — около 2 140 запросов в секунду. Основной поток — свыше 30 тысяч ходов в секунду — идёт по WebSocket напрямую в пять игровых регионов. Поэтому ход не проходит через центральный API. Это сокращает сетевой путь и позволяет масштабировать игровые серверы независимо.

## Слайд 3. Балансировка и маршрутизация

Для центрального API используется один внешний AWS NLB. Route 53 разрешает доменное имя, NLB распределяет TCP-соединения между тремя NGINX, а NGINX завершает TLS. Затем API Gateway на базе Envoy выбирает доступный экземпляр микросервиса. Отдельный внутренний L4 не использовался.

Игровое подключение устроено иначе. Matchmaking выбирает регион (наиболее подходящий для 2 игроков) и конкретный Game service — владельца партии, учитывая задержку и загрузку. Оба игрока получают его адрес и подключаются напрямую по WSS. Поэтому игровые NLB и NGINX мы исключили: каждый ход не требует лишнего проксирования. При отказе клиент запрашивает новый адрес владельца.

## Слайд 4. Архитектура проекта

Система разделена на три области. **Virginia API** отвечает за точку входа и матчмейкинг. В **пяти игровых регионах** Game service обрабатывает ходы, Redis хранит текущее состояние, а региональная Kafka — подтверждённые события. **Virginia Storage** отвечает за постоянные данные и фоновые задачи.

После завершения партии MirrorMaker 2 передаёт `game.finished` в центральную Kafka. Далее независимо запускаются сохранение партии и истории, пересчёт рейтинга и Stockfish. PostgreSQL хранит оперативные данные, ClickHouse — архив, Ceph и S3 — резервные копии. Тяжёлая обработка не входит в путь очередного игрового хода.

## Слайд 5. Резервирование и восстановление партии

Каждый игровой регион содержит три зоны доступности. Региональная Kafka использует три брокера и три копии каждого критического события. При `min.insync.replicas=2` и `acks=all` Game service подтверждает ход только после необходимой фиксации в журнале. Поэтому ход не остаётся исключительно в оперативной памяти игрового сервера.

Redis состоит из трёх основных узлов и трёх реплик. Он ускоряет работу с текущей позицией, но его состояние можно восстановить из Kafka. PostgreSQL в Virginia резервируется отдельно: один основной экземпляр и две реплики.

Если Game service падает, новый владелец считывает контрольную точку и последующие подтверждённые ходы, восстанавливает позицию и часы, обновляет Redis. Механизм **fencing** запрещает старому владельцу подтверждать ходы. Затем игроки переподключаются. Это проектный сценарий отказоустойчивости, который необходимо проверить тестами.

## Слайд 6. Событийная обработка без задержки игровых ходов

После окончания партии начинается асинхронная обработка. MirrorMaker 2 передаёт в Virginia только событие завершения, а не все игровые ходы. Центральная Kafka распределяет работу между независимыми группами потребителей.

Сначала **Game Persistence Worker** сохраняет партию и историю двух игроков в PostgreSQL и публикует `game.persisted`. После этого Rating Worker обновляет рейтинг, а архивный потребитель переносит данные в ClickHouse. Параллельно Analysis Dispatcher ставит задачу `analysis.tasks`. Stockfish публикует `analysis.finished`, а Analysis Persistence сохраняет результат и отправляет `analysis.persisted`.

Поэтому задержка Stockfish или ClickHouse не блокирует игру. Повторные события обрабатываются идемпотентно; OUTBOX в текущей архитектуре не используется.

## Слайд 7. Обоснование игровых мощностей

Рассчитаем игровые серверы. При пике 30 400 ходов в секунду и пяти регионах получается 6 080 ходов в секунду на регион. В каждом предусмотрено шесть Game service — по два в каждой зоне доступности.

При отказе одной зоны остаются четыре сервера. Если один сервер выдерживает расчётные две тысячи ходов в секунду, суммарная мощность составляет восемь тысяч. Это примерно на 32 процента больше требуемой нагрузки. Таким образом, всего нужно 30 игровых серверов.

Но две тысячи ходов в секунду — пока **проектная цель**, а не измеренный результат. Её и число одновременных WSS нужно подтвердить нагрузочными тестами.

## Слайд 8. Итог проектирования

В результате мы получили архитектуру с разной балансировкой API и игр, реплицируемым журналом ходов, восстановлением после отказов и независимой фоновой обработкой. Предварительно рассчитаны 174 основные виртуальные машины, 375 машин Stockfish и около 1,45 петабайта дисков. Следующий шаг — испытания производительности и сценариев отказа. Спасибо за внимание.
